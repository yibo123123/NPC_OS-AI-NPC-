## 第一章：设计理念 —— 约束驱动的认知架构

### 1.1 核心问题

当前 AI NPC 领域面临一个根本性矛盾：**真实的虚拟生命需要稳定的人格内核，而大语言模型天生不稳定。**

LLM 的本质是概率生成——同一个 prompt 每次输出不同。这意味着基于 LLM 的 NPC 没有"性格一致性"：今天的 NPC 和明天的 NPC 可能行为矛盾，甚至同一段对话前后矛盾。

### 1.2 设计原则

NPC_OS 的设计从五个核心约束出发，**这些约束不是限制，而是保证 NPC 可信的锚点**：

| # | 约束 | 含义 | 为什么需要 |
|---|---|---|---|
| C1 | **人格不变** | OCEAN 五参数全生命周期不变 | NPC 的"本性"不随对话漂移 |
| C2 | **行为修正有界** | 所有行为偏离人格基线 ≤ ±30% | NPC 可以适应情境，但不会"变成另一个人" |
| C3 | **认知分层** | 短期反应 ≠ 长期习惯 ≠ 核心信念 | 人类不会因为今天心情不好就改变世界观 |
| C4 | **记忆有损** | 容量有限、重要性筛选、随时间衰减 | 真实的记忆是不完美的，完美记忆是反人性的 |
| C5 | **LLM 是工具，不是大脑** | LLM 只负责语言表达，不负责决策 | 逻辑决策不可交给概率模型 |

### 1.3 设计哲学的工程映射

```
约束 → 系统设计 → 代码结构 → 测试验证
  C1   → OCEAN 锚定  → Core 冻结  → personality_never_drifts (hypothesis)
  C2   → ±30% 限幅   → 行为权重钳位 → behavior_bounded
  C3   → 三层认知    → 独立 Service → cognitive_layers
  C4   → 容量上限    → MemoryService → memory_never_exceeds_limit
  C5   → LLM 解耦    → 可选适配器   → 零 LLM Tick 运行
```

**这是本引擎最核心的原创理念**：不是通过更聪明的 AI 让 NPC 变可信，而是通过精心设计的心理约束让 NPC 的行为边界与人类的心理边界对齐。

## 第二章：系统架构 —— 六层冻结 + 单向依赖

### 2.1 层级结构

NPC_OS 采用严格单向依赖的六层架构。每一层只能依赖正下方的一层，**反向依赖被架构纪律禁止**。

```
交互方向     ┌─────────────────────────────────────┐
             │          UI Layer（用户界面）         │
使用者 →     ├─────────────────────────────────────┤
             │       Controller Layer（控制层）       │  参数校验/异常封装
             ├─────────────────────────────────────┤
             │        Bridge Layer（桥接层）         │  参数透传/日志
             ├─────────────────────────────────────┤
             │       Runtime Layer（运行时层）       │  全局调度/状态管理
             ├─────────────────────────────────────┤
             │        Service Layer（服务层）        │  业务流程编排
             ├─────────────────────────────────────┤
             │     Core Layer（核心层）【冻结】      │  原子能力/数据模型
             └─────────────────────────────────────┘
                       数据流向 →
```

### 2.2 冻结机制

Core 层是整个架构的基石，一旦通过审计测试即**永久冻结**：

| 冻结策略 | 内容 | 例外规则 |
|---|---|---|
| 禁止修改已有方法签名 | 所有公有方法参数不可变 | 新增方法必须带默认值 |
| 禁止删除公有接口 | 已有 API 永久保留 | 可标记 @deprecated |
| 禁止修改数据类字段 | dataclass 字段不可删/改名 | 可新增 Optional 字段 |
| 禁止修改算法逻辑 | 核心算法的行为不可变 | 仅允许性能优化（结果不变） |

### 2.3 依赖注入

引擎采用 Composition Root 模式管理服务依赖：

```
CompositionRoot
  ├── _build_core()         → EventBus, MemoryService, RelationshipService, LLM
  ├── _build_memory_layer() → MemoryManager, MemoryAdapter, ShortTermMemory, WorkingMemory
  ├── _build_services()     → ChatService, GoalOrchestrator, ReflectionService 等 16+ 服务
  └── _build_runtimes()     → WorldRuntime, BehaviorRuntime, ChatRuntime, SocialRuntime
```

每个服务通过 ServiceContainer（DI 容器）获取依赖，不直接构造。所有服务的生命周期由容器统一管理。

在 MainRuntime 层面，所有服务的构造全权委托给 RuntimeFactory，确保运行时类中零直接 `self.xxx = XxxService()` 构造代码。

## 第三章：人格/情绪/记忆系统 —— OCEAN + VAD + 三层认知

### 3.1 人格系统（OCEAN 大五模型）

人格是 NPC 一切行为的底层锚定点。NPC_OS 采用心理学界公认的大五人格模型（Big Five / OCEAN）：

| 维度 | 高值表现 | 低值表现 | 影响的行为域 |
|---|---|---|---|
| **O**penness 开放性 | 好奇、创新、冒险 | 传统、务实、保守 | 学习意愿、对新事物的反应 |
| **C**onscientiousness 尽责性 | 自律、有计划、可靠 | 随性、拖延、灵活 | 日程遵守、目标坚持度 |
| **E**xtraversion 外向性 | 活跃、社交、热情 | 安静、独处、内省 | 社交频率、群体行为 |
| **A**greeableness 宜人性 | 合作、信任、共情 | 竞争、怀疑、直接 | 冲突概率、关系建立 |
| **N**euroticism 神经质 | 敏感、焦虑、情绪化 | 稳定、冷静、韧性 | 情绪波动幅度、压力反应 |

**人格不变证明**：在 hypothesis 随机测试中（1-500 tick 随机），所有 NPC 的 OCEAN 五参数在任意运行时长后保持初始值不变。**人格漂移 = 0。**（验证代码：`tests/test_v12_invariants.py` · 20 次随机参数）

### 3.2 情绪系统（VAD 三维模型）

情绪系统基于心理学的效价-唤醒-支配（Valence-Arousal-Dominance, VAD）模型：

| 维度 | 范围 | 含义 |
|---|---|---|
| **Valence 效价** | [-1, 1] | 正负情感（愉悦—不悦） |
| **Arousal 唤醒** | [0, 1] | 激活程度（平静—激动） |
| **Dominance 支配** | [0, 1] | 控制感（顺从—支配） |

**情绪动力学**：

```
每 Tick:  情绪 → 回归中性 (decay)
事件触发: 事件 → 情绪偏移 (delta)
人格调节: Neuroticism → 情绪波动幅度
```

**情绪边界证明**：hypothesis 验证 emotion.valence ∈ [0, 1] 在任意 tick 成立——不溢出、不越界。（验证代码：`tests/test_v12_invariants.py` · 20 次随机参数）

### 3.3 记忆系统（三层结构）

NPC_OS 实现三层记忆架构，模拟人类记忆的层次化特性：

| 记忆层 | 容量 | 持续时间 | 存储方式 | 检索方式 |
|---|---|---|---|---|
| **短期记忆** | 50 条 | 数小时 | 环形缓冲区 | 顺序最近 |
| **工作记忆** | 7±2 条 | Tick 级 | 显式焦点集 | 当前上下文 |
| **长期记忆** | 500 条/NPC | 持久化 | 重要性索引 | 加权检索 |

**记忆容量证明**：hypothesis 验证单 NPC 记忆 ≤ 500，且记忆数单调不减（不会被静默删除）。（验证代码：`tests/test_v12_invariants.py` · 20 次随机参数）

### 3.4 三层认知架构

认知系统将 NPC 的"心理活动"分为三个层次，对应不同的时间尺度和稳定性：

```
第一层: 短期倾向 (状态性)
  ├── 情绪波动、即时需求、当前感知
  ├── 每 Tick 更新
  └── 高频率、低幅度

第二层: 长期习惯 (特质性)
  ├── 行为偏好、技能熟练度、互动模式
  ├── 跨 Tick 累积
  └── 中频率、中幅度

第三层: 核心信念 (身份性)
  ├── 自我认知、价值观、世界观片段
  ├── 跨会话持久
  └── 低频率、高幅度（仅在重大经历后更新）
```

**这一分层设计确保 NPC 不会因为一次挫折就改变三观，也不会因为长期习惯而在紧急情况下反应迟钝——与人类心理的时间尺度对齐。**

## 第四章：叙事记忆修订与认知综合 —— Rule A~E

这是 NPC_OS 最具原创性的子系统。它不是从学术界论文复制的，而是从叙事心理学（McAdams 叙事身份理论）中提取核心概念后，独立设计的实现。

### 4.1 核心动机

真实的"自我"不是一个静态标签，而是一个**不断讲述、修订和综合的人生故事**。人类通过将经历组织成叙事来建构身份。NPC_OS 的叙事记忆系统模拟了这一过程。

### 4.2 规则系统

引擎定义了五条递进规则，将原始事件一步步加工为成熟的身份叙事：

```
LifeEvent（原始事件）
    │
    ├── Rule A: 重大事件 → 单次叙事
    │   （importance ≥ 0.7 的事件被编码为叙事单元）
    │
    ├── Rule B: 重复模式 → 身份叙事
    │   （同一类型事件出现 ≥ 3 次，抽象为模式认知）
    │
    ├── Rule C: 通用强化
    │   （所有叙事随正面/负面经历被强化或弱化）
    │
    ├── Rule D: 认知修订
    │   （当叙事带来持续负面情绪时，NPC 可"重新诠释"过去）
    │   │   ├── struggle → resilience
    │   │   ├── loneliness → selective bonding
    │   │   ├── failure → refocused effort
    │   │   ├── distrust → cautious trust
    │   │   └── burnout → balanced living
    │   │
    └── Rule E: 认知综合（最高层）
        （当 NPC 持有两个冲突的叙事时，
         在更高层次上综合出"领悟"）
         │   冲突对示例:
         ├── "我被世界伤害" vs "我被世界善待"
         │   → 综合: "世界是复杂的，既有伤害也有善意"
         ├── "我很有能力" vs "我经常失败"
         │   → 综合: "能力需要在对的方向上验证"
         └── ...
```

### 4.3 表达输出

经过叙事系统加工的 NPC 自我认知，在对话中表现为三层表达：

```
第一层: 人生叙事 —— "我经历过..."
          原始经历的陈述
第二层: 内心矛盾 —— "但我有时会想..."
          冲突认知的表达
第三层: 人生领悟 —— "后来我明白了..."
          认知综合的输出
```

这种三层表达使 NPC 的对话不再是事实的堆砌，而是**有深度、有成长轨迹、有人生厚度**的交流。

## 第五章：社会涌现与行为验证 —— 6 维指标 + 4 大场景

### 5.1 社会网络系统

多 NPC 环境下，引擎构建完整的社会关系图：

| 机制 | 描述 | 建模方式 |
|---|---|---|
| **关系网络** | NPC 之间的定向关系图 | 信任度 × 亲密度 二维边权重 |
| **信息传播** | 八卦/知识/谣言在社会网络中的扩散 | BFS 传播 + trust × familiarity 概率衰减 |
| **社交影响** | NPC 之间的信念/情绪相互影响 | 影响力评分 + 情绪传播模型 |
| **社群发现** | 自动识别 NPC 社交子群 | BFS 团发现算法 |

### 5.2 涌现行为（Emergent Behavior）

NPC_OS 的关键特征：**NPC 的社会行为不是脚本编写的，而是从个体交互中自然涌现的。**

已确认的涌现现象：

| 涌现现象 | 触发条件 | 表现形式 |
|---|---|---|
| **友谊圈形成** | 高频积极互动 | 3-5 NPC 自动形成稳定社交群体 |
| **信息级联** | 高信任链路 | 信息在网络中快速扩散至全群 |
| **社会分化** | 价值观冲突 | NPC 群自动分为立场不同的子群 |
| **社群演化** | 长时间模拟 | 社群分裂、合并、领袖交替 |

### 5.3 行为验证框架（4 大场景）

为了证明 NPC 的行为是模拟驱动的而非随机生成，引擎内置了行为验证框架：

| 验证场景 | 验证目标 | 量化指标 |
|---|---|---|
| **关系演进** | 关系强度随时间单调变化 | 因果关系 ≥ 0.8 |
| **人格差异** | 不同人格 NPC 行为显著不同 | 组间方差 > 组内方差 3× |
| **长期影响** | 经历在 1000 tick 后仍影响行为 | 相关性 > 0.5 |
| **记忆影响** | 记忆内容影响决策 | 记忆相关决策占比 > 60% |

**验证结论**：NPC 行为满足因果性、动态性、非随机性和人格差异性四个条件——**这不是聊天机器人，而是真正的模拟驱动行为。**

### 5.4 社会涌现六维指标

| 指标 | 含义 | 取值范围 |
|---|---|---|
| **密度** | 社交连接紧密程度 | [0, 1] |
| **社群数** | 子群数量 | [1, N] |
| **可达性** | 信息可触达范围 | [0, 1] |
| **影响力集中度** | 关键节点的控制程度 | [0, 1] |
| **涌现事件数** | 自发涌现的非预设事件 | ≥ 0 |
| **多样性** | NPC 行为分化程度 | [0, 1] |

## 第六章：工程保障 —— TickBudget / 形式化不变量 / 零噪音日志

### 6.1 分层 Tick 调度（TickBudgetManager）

NPC 的 Tick 循环包含数十项子系统任务。为在大规模场景下保持性能，引擎实现了 9 级分层调度：

| 级别 | 频率 | 模块 | 调度策略 |
|---|---|---|---|
| **Critical** | 每 Tick | emotion, need, perception, decision | 无延迟，每 Tick 必执行 |
| **Fast** | 每 3 Tick | motivation | 轻量级，快速轮询 |
| **Medium** | 每 10 Tick | social_cognition | 社交认知，批次可接受 |
| **Slow** | 每 30 Tick | consolidation | 记忆巩固，不需实时 |
| **Background** | 每 60 Tick | reflection | 深度反思，允许延迟 |
| **Rare** | 每 100 Tick | narrative_decay | 叙事衰减，低频即可 |
| **Very Rare** | 每 300 Tick | learning | 决策学习，长周期 |
| **Extremely Rare** | 每 500 Tick | personality_evolution | 人格演化，极低频 |
| **Almost Never** | 每 5,000 Tick | cognitive_review | 认知回顾，几乎不跑 |

**性能效果**：在 100 NPC × 100 Tick 的基准测试中，平均 Tick 延迟 < 50ms，相比无调度版本提升约 50 倍。（基准代码：`tests/test_v11_100npc_benchmark.py`）

### 6.2 增量保存系统

全量序列化在 500 NPC 场景下需约 2,500ms。为解决此问题，引擎实现了增量保存：

| 策略 | 机制 | 效果 |
|---|---|---|
| **脏标记追踪** | 7 种状态标记 — NPC/记忆/情绪/关系/目标/创建/删除 | 50k 标记 < 50ms |
| **智能全量/增量切换** | dirty < 5% 时增量保存，> 90% 时触发全量 | 20 次增量后自动全量 |
| **格式兼容** | V9.4.3 旧格式可加载 | 无数据迁移成本 |

### 6.3 形式化不变量（hypothesis 验证）

引擎采用 property-based testing（假设检验）证明核心不变量。测试随机生成边界条件，验证系统在任何输入下保持正确：

| 单 NPC 记忆 ≤ 500 | 1-500 tick 随机参数 | 20 次×随机 |
| 记忆单调不减 | 1-500 tick 随机参数 | 20 次×随机 |
| NPC 数量守恒 | 1-500 tick 随机参数 | 20 次×随机 |

## 第七章：实验验证 —— 100 NPC / 30 天 / 性能基准

### 7.1 规模基准

| 规模 | NPC 数 | 记忆数 | 平均 Tick 延迟 | 内存占用 |
|---|---|---|---|---|
| Small | 10 | 100/NPC | <2ms | ~50MB |

## 第九章：行业趋势分析

本章节仅探讨技术演进方向与场景适配潜力，不构成任何商业要约或合作邀约。

### 9.1 游戏产业的三重困境

当前游戏产业在 NPC 技术上正面临三个相互强化的结构性矛盾：

#### 困境一：规模与深度的零和博弈

开放世界的规模快速扩张，但 NPC 交互深度反而下降。一个典型的 3A 开放世界包含数百个 NPC，但超过 80% 仅提供预设对话线或重复行为。开发者被迫在"更多 NPC"和"更智能的 NPC"之间做零和选择——因为传统行为树/状态机方法下，每个智能 NPC 的开发成本呈线性增长。

#### 困境二：LLM 的"伪解"陷阱

2023-2025 年间，行业普遍将 LLM 视为 NPC 智能化的终极方案，但这个路径正在暴露根本性缺陷：

| 维度 | LLM 方案表现 | 根因 |
|---|---|---|
| **人格一致性** | 差——每次 prompt 可能输出矛盾 | LLM 是概率模型，无稳定状态 |
| **运行成本** | 高——每句对话需调用云端 API | Transformer 推理无法本地化 |
| **可解释性** | 无——黑盒输出不可审计 | 无法追溯决策路径 |
| **监管风险** | 高——内容合规不可控 | 生成内容无法预先约束 |
| **离线能力** | 无——必须联网 | 依赖云端推理 |

这些不是可优化的问题，而是 LLM 架构本身的结构性局限。行业内已有头部项目因 LLM 成本过高或内容合规问题而放弃或回滚 AI NPC 计划。

#### 困境三：玩家体验通胀

玩家的期望曲线在过去十年急剧攀升：从"有对话的 NPC"到"有性格的 NPC"到"有记忆的 NPC"再到"会记住我的 NPC"。市场没有有效的供给——不是不想做，而是没有可行的技术路径。

### 9.2 从概率生成到确定性模拟：架构范式的必要转移

NPC_OS 对上述困境的回应不是更聪明的 AI，而是**架构层级的范式转移**：

```
LLM 范式:         NLP Prompt → 概率采样 → 对话文本
NPC_OS 范式: 约束驱动的认知模型 → 状态机 → 行为决策 → 对话表达
                 ↑ 确定性算法       ↓  可选 LLM（仅语言层）
```

这一转移的本质是将 NPC 行为从"生成"还原为"模拟"——从不可控的概率输出转变为受约束的确定性行为，同时保留 LLM 作为可选的语言表达层。
